# **Merge Conflict Resolution: Classification or Generation?**

MergeGen is a generation-based merge conflict resolution approach: it represents conflicts in a structured way and uses an encoder-decoder model (CodeT5) to generate the resolution token by token. This repository is the replication package of the paper (`Merge Conflict Resolution- Classification or Generation.pdf`), adapted to run on Windows with a single GPU.

## **Structure**

| Path | What it is |
|---|---|
| `prepare_raw_data.py` | Builds `RAW_DATA/raw_data` with every conflict of a language |
| `prepare_toy.py` | Builds `RAW_DATA/raw_data` with the first N conflicts of a language (quick tests) |
| `runtotal_dataset.py` + `dataset_parallel.py` | Parallel pre-processing (token-level merge with `git merge-file`) → `PROCESSED/` |
| `dataset.py` | Combines the `PROCESSED/` chunks and splits them into train/validation/test (8:1:1) |
| `run_mergegen.py` | Model, training (`train`), validation (`dev`) and testing (`test`) |
| `run_claude.py` | Resolves the same test examples with the Claude API, for comparison |
| `archive_run.py` | Archives the artifacts of a run into `runs/<name>/` and cleans the project |
| `codet5-small/` | Local copy of the base model (not versioned) |
| `RAW_DATA/fse2022/` | MergeBERT dataset downloaded from Zenodo (not versioned) |
| `OUTPUT/test_output_old.txt` | Resolutions generated by the original authors |

## **Setup (once)**

### 1. Environment

```sh
conda create -n ase-merge python=3.8
conda activate ase-merge
python -m pip install -r packages.txt -f https://download.pytorch.org/whl/torch_stable.html
```

The `-f` flag lets pip find PyTorch with CUDA (`torch==1.10.1+cu113`). `leven` and `tree-sitter` are commented out in `packages.txt`: they need a C++ compiler on Windows and are not used by the project.

### 2. Base model

With `transformers==4.19.2`, downloading `Salesforce/codet5-small` automatically fails (the Hugging Face Hub now answers with relative redirects, which this version does not handle). That is why the code loads the model from `./codet5-small`. Download it once (requires [git-lfs](https://git-lfs.com/)):

```sh
git lfs install
git clone https://huggingface.co/Salesforce/codet5-small
```

### 3. Data

Download the MergeBERT dataset [1] from [Zenodo](https://zenodo.org/record/6366908) and extract it into `RAW_DATA/fse2022/`, so that `RAW_DATA/fse2022/automated-analysis-data/<Language>/` exists (`Java`, `CSharp`, `JavaScript`, `TypeScript`).

## **Running a pipeline**

Run everything from the project root with the environment active (`conda activate ase-merge`). `runtotal_dataset.py` calls `python` by name, so it must resolve to the environment's Python.

### 1. Check that the project is clean

Files from a previous run are **silently reused**: if `processed_*.pkl` exist, `dataset.py` does not rebuild the data, and if `best_model.pt` exists, training resumes from it.

```sh
python archive_run.py --dry-run check
```

If anything shows up besides `copia RAW_DATA\...` and `move RESULTS` (the empty folder), archive the previous run first (step 6).

### 2. Build the examples

For quick tests, the first N conflicts of a language (in id order):

```sh
python prepare_toy.py 400 Java
```

For a whole language, as in the paper (the paper trains and evaluates each language separately):

```sh
python prepare_raw_data.py Java
```

Both write `RAW_DATA/raw_data` and `RAW_DATA/raw_data_ids.json` (the origin of each example: language, file id, conflict index).

### 3. Pre-process

```sh
python runtotal_dataset.py dataset_parallel.py
```

Produces `PROCESSED/processed_<start>_<end>.pkl` (chunks of 1000 examples) and temporary files in `GIT_MERGE_FILES/`.

> **Full dataset:** `runtotal_dataset.py` runs up to `max_num = 100` subprocesses at once, and each one loads the whole `raw_data`. On a regular machine this exhausts memory; lower `max_num` (e.g. to 4–8) before running a whole language.

### 4. Train

```sh
python run_mergegen.py train
```

On the first run, `dataset.py` creates `processed_train.pkl`, `processed_valid.pkl`, `processed_test.pkl` and `all_index` (the 8:1:1 split, always the same for the same `raw_data`). The best model on the validation set is saved to `best_model.pt`, and per-epoch progress to `OUTPUT/train_process`. Training stops by itself after several epochs without improvement.

### 5. Test

```sh
python run_mergegen.py test
```

| Output | Content |
|---|---|
| `OUTPUT/test_process` | Exact-match accuracy on validation and test (the main result) |
| `OUTPUT/test_OUTPUT/SUCCEED/` and `FAIL/` | One file per test example, with the expected and generated resolutions |
| `OUTPUT/total_gen_output_test_beam.json` | All generated resolutions |
| `RESULTS/test_gen_exactly_match_ids` | Positions (within the test set) of the correctly resolved examples |

`SUCCEED` + `FAIL` add up to the size of the test set (10% of the examples).

### 6. Archive

```sh
python archive_run.py --dry-run toy400-java
python archive_run.py toy400-java
```

Moves the split, model, logs and outputs into `runs/<name>/`, copies `raw_data` and `raw_data_ids.json`, deletes `PROCESSED/` and `GIT_MERGE_FILES/`, and writes `runs/<name>/run_info.json` with the number of examples, the split and the accuracy. The project is then clean for the next run (go back to step 2).

Each run's `raw_data` and `all_index` (`test` key) make it possible to evaluate other approaches on exactly the same test examples (see below).

## **Resolving with the Claude API**

`run_claude.py` sends each test conflict to Claude and measures exact-match accuracy on the same examples MergeGen was tested on. It needs only the packages in `requirements-claude.txt`; `anthropic` requires Python ≥ 3.10 — so it runs in its own virtual environment, **not** in `ase-merge` (Python 3.8). Create it once (with any Python ≥ 3.10; on Windows, `py -3.14` picks the version):

```sh
py -3.14 -m venv .venv-claude
.venv-claude\Scripts\python -m pip install -r requirements-claude.txt
```

Activate it before running (`conda deactivate` first if `ase-merge` is active):

```sh
.venv-claude\Scripts\Activate.ps1
```

On cmd use `.venv-claude\Scripts\activate.bat`; on Git Bash, `source .venv-claude/Scripts/activate`.

Put the API key in a `.env` file at the project root (it is git-ignored):

```sh
ANTHROPIC_API_KEY=sk-ant-...
```

A `ANTHROPIC_API_KEY` already set in the environment takes precedence over the `.env`.

With an Organization-scoped API key, also set `ANTHROPIC_WORKSPACE_ID` (the ID of the workspace to use); workspace-scoped keys do not need it.

Run it after step 5 (test), or on an archived run with `--run`:

```sh
python run_claude.py --limit 5
python run_claude.py --run runs/toy400-java
```

| Option | Default | What it does |
|---|---|---|
| `--run DIR` | `.` | Folder with `RAW_DATA/raw_data`, `RAW_DATA/raw_data_ids.json` and `all_index` |
| `--split` | `test` | `test` or `valid` |
| `--limit N` | all | Only the first N examples of the split (cheap trial runs) |
| `--model` | `claude-opus-5-5` | Claude model |
| `--effort` | `medium` | `low` … `max`: how much the model thinks (and spends) per conflict |
| `--workers` | `4` | Simultaneous requests |

Each conflict is shown as diff3 markers (ours / base / theirs) with its context lines kept apart, and Claude answers with the resolved region only. The accuracy uses the same whitespace normalization as the pre-processing; the only difference is that MergeGen truncates the reference at 200 tokens, while here the full reference is compared.

Outputs go to `<DIR>/OUTPUT/claude/<model>/<split>/`:

| Output | Content |
|---|---|
| `summary.json` | Exact-match accuracy, positions of the correct examples (as in `RESULTS/test_gen_exactly_match_ids`), refusals and tokens used |
| `results.jsonl` | One line per example with the generated resolution |
| `SUCCEED/` and `FAIL/` | One file per example, as in `OUTPUT/test_OUTPUT` |

`results.jsonl` is also the resume point: examples already there are skipped, so an interrupted run (or one with API errors) continues where it stopped when run again. Delete the folder to start over. `archive_run.py` moves `OUTPUT/claude` along with the rest of the run.

## **Data format**

The original README did not describe how to build `RAW_DATA/raw_data`; the `prepare_*` scripts reconstruct this step from the paper:

- **One example per conflict**, not per file. Conflicts come from the `conflicting_chunks` field of the `<id>_metadata.json` files.
- **Input:** base, a and b = 2 lines of context before + that version's snippet + 2 lines after (`CONTEXT_LINES` in `prepare_raw_data.py`). The paper does not state how much context it uses; with 2 lines, 94.8% of the inputs fit in 500 tokens (the paper cites 95%).
- **Expected output:** `res_region`, the developer's resolution of that snippet.
- **Discarded:** conflicts with no resolution found, whose resolved file is empty (`RES_FILE_EMPTY`), with corrupted metadata, or from minified files.

Since this reconstruction is an inference, the numbers may not match the paper exactly.

## **Changes from the original code**

- Base model loaded from `./codet5-small` (see Setup, step 2).
- `AdamW` imported from `torch.optim` (removed from `transformers` in recent versions).
- `model.module` → `model` when saving and loading the checkpoint, to run on a single GPU.
- `encoding='utf-8'` when reading and writing code (the Windows default, cp1252, breaks on non-ASCII characters).
- Training with batches of 7 and gradient accumulation over 5 steps (effective batch of 35, as in the original), to fit an 8 GB GPU. Tune `batch_size` and `grad_accum_steps` in `run_mergegen.py`.
- `packages.txt` adapted to the environment that worked (PyTorch `cu113`, no `mkl-*` packages).
